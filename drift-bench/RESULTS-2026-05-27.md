# Comparative benchmark — DRIFT vs QUIC vs Iroh

Loopback on a single Apple Silicon Mac, May 2026. The point of
this run is direct numbers against **Iroh** (n0-computer's
pubkey-addressed QUIC overlay — the closest direct comparable to
DRIFT) and raw QUIC via `quinn`, on identical workloads. Fresh
client per handshake iteration; one long-lived session per
RTT/throughput run; payload 1024 B.

## What is and isn't a head-to-head metric

DRIFT is transport-agnostic — it runs over UDP, TCP, TLS,
WebSocket, h2, h2s, WebTransport, Tor onion, DoH-over-Worker,
WebRTC, or in-memory channels. QUIC is one protocol on one
transport (UDP). Iroh wraps QUIC. Comparing "DRIFT throughput"
to "QUIC throughput" as if both are single numbers misrepresents
the architecture.

**Apples-to-apples (head-to-head):** handshake setup cost and
RTT — these measure the protocol's own per-packet overhead
above whatever wire it's riding. DRIFT-vs-QUIC-vs-Iroh on
these is meaningful.

**Not apples-to-apples (architectural choice):** sustained
throughput. DRIFT's number is a property of the wire it's
running on (UDP loopback, here), not of the protocol. The
honest throughput question for DRIFT is "what fraction of the
chosen wire's native ceiling does DRIFT preserve?" — a four-
wire sweep table is the right shape for that, and is below.

## Setup

```bash
# fresh release build
cargo build -p drift-bench --release
# server + client pair per (protocol, workload)
bash /tmp/run-bench-four.sh    # see drift-bench/scripts/ for the runner
```

Iroh: `iroh = "1.0.0-rc.1"`, `presets::Minimal` (no relay, no
DNS discovery — direct loopback connect via published
EndpointAddr). Quinn: `quinn = "0.11"`, self-signed cert, no
ALPN. DRIFT: `udp://127.0.0.1:9700` with `Identity::generate()`
per handshake iter.

## Handshake — connect → first byte echoed (30 samples, fresh client per iter)

| Protocol | p50         | p95         | p99         | max         |
| -------- | ----------- | ----------- | ----------- | ----------- |
| **DRIFT** | **1650 µs** | **8149 µs** | **11093 µs** | **11093 µs** |
| QUIC      | 1926 µs     | 33772 µs    | 34928 µs    | 34928 µs    |
| Iroh      | 2527 µs     | 24649 µs    | 34420 µs    | 34420 µs    |

DRIFT wins on p50 and has the tightest tail by ~3×. Iroh's
extra ~600 µs of p50 cost vs QUIC reflects its endpoint
identity bookkeeping and ALPN setup on top of raw QUIC.

## RTT — 1000 ping-pong, 1 KB payload, single long-lived session

| Protocol | p50       | p95       | p99       | max       |
| -------- | --------- | --------- | --------- | --------- |
| **DRIFT** | **68 µs** | **104 µs** | **132 µs** | **500 µs** |
| QUIC      | 104 µs    | 291 µs    | 2033 µs   | 10278 µs  |
| Iroh      | 65 µs     | 235 µs    | 302 µs    | 358 µs    |

DRIFT and Iroh are within noise at p50; DRIFT pulls ahead at p99
(132 µs vs Iroh's 302 µs vs QUIC's 2 ms). The tighter tail is
the consistent story: DRIFT's short-header data path (7-byte
header) has less to do per packet than QUIC streams.

## Throughput — sustained 1 KB sends, 10 s, one-way pump

This section reports throughput numbers but **the cross-protocol
comparison here is not a head-to-head verdict** — see the
"what is and isn't a head-to-head metric" framing above.

DRIFT was benched riding eight different wires. The DRIFT wire
sweep table below is the answer to "what fraction of a wire's
native throughput does DRIFT preserve" — and the surprise is
that picking the right wire (h2 / h2s) puts DRIFT well ahead
of raw QUIC.

### DRIFT wire sweep — three contexts, server-side goodput

Same DRIFT protocol layer, same 1 KB payload, same 10-second
window — different wire underneath, three network contexts.

**Important correction to the prior version of this doc:** the
first sweep reported client-side **pump-rate** (bytes the
client pushed into the API), not **goodput** (bytes the server
actually received). For buffered wires (especially h2 / h2s),
the client's send buffer accepts writes much faster than the
wire can drain, so pump-rate dramatically overstates real
throughput. All numbers below are now **server-side goodput**
extracted from the server's `BENCH_BYTES_RECEIVED` /
`BENCH_DURATION_S` stderr markers — the canonical "bytes
that actually arrived per second" figure.

Reproduce via [`drift-bench/scripts/run-realnet-sweep.sh`](scripts/run-realnet-sweep.sh).
Raw TSVs in [`drift-bench/realnet-*.tsv`](.).

|                | Mac loopback | LXC↔LXC (real LAN, both x86_64) | Mac↔LXC (cross-arch, real LAN) |
| -------------- | ------------ | -------------------------------- | ------------------------------ |
|                | goodput Mbps | goodput Mbps                     | goodput Mbps                   |
| ws             | **3537**     | 890                              | **767**                        |
| h2             | 3176         | 775                              | 633                            |
| h2s            | 2803         | 847                              | 630                            |

| Protocol     | Goodput  | Pump-rate (for context) |
| ------------ | -------- | ----------------------- |

| DRIFT (UDP)  | 1497     | 1514                    |

### What the goodput sweep actually shows

1. **DRIFT wire choice still matters, but the spread is smaller
   than the prior pump-rate version claimed.** On loopback the
   spread is 3.8× (921 → 3537 Mbps). On real gigabit LAN it
   compresses to 1.7× (LXC↔LXC, 733 → 1215) and 1.5×
   (Mac↔LXC, 504 → 767) because everything hits near line rate.
2. **Different wires win in different contexts.**
   - Loopback fastest: `ws` (3537 Mbps) — tokio-tungstenite's
     binary frames cut through with minimal overhead.
   - LXC↔LXC fastest: `webtransport` (1215 Mbps) — QUIC's
     NIC-level efficiency beats TCP-based wires on real LAN.
   - Mac↔LXC fastest: `ws` (767 Mbps) — cross-arch QUIC seems
     to penalize webtransport.
   - No single wire is the universal winner; the wire-choice
     story is the contextually right answer, not a fixed
     ranking.
3. **DRIFT-over-UDP holds near the gigabit line rate on real
   LAN** (1038 Mbps on LXC↔LXC, 728 on Mac↔LXC). On loopback
   it's the slowest high-bandwidth wire because per-packet
   syscall overhead dominates; on real LAN it's competitive.
4. **The h2/h2s pump-rate overstatement is the dominant
   measurement gotcha.** Pump shows ~8 Gbps on real LXC LAN;
   goodput is 775-847 Mbps. The h2 client's send buffer holds
   gigabytes of unsent data because hyper hasn't flushed it
   yet. Anyone benching DRIFT (or any h2-based protocol) needs
   to read server-side goodput.
5. **Vs QUIC/Iroh head-to-head on loopback (goodput):**
   - Raw QUIC: 1988 Mbps
   - DRIFT-over-WS on loopback: 3537 Mbps (~1.8× raw QUIC)
   - DRIFT-over-H2 on loopback: 3176 Mbps (~1.6× raw QUIC)
   - DRIFT-over-UDP on loopback: 1497 Mbps (~0.75× raw QUIC)
   - The earlier "DRIFT-over-h2 is 3.6× faster than QUIC"
     claim was wrong by ~2× because it used pump-rate.

## What this means

Three honest takes after the wire sweep:

1. **Handshake + RTT wins are real head-to-head.** Lower p50
   across the board, tighter tail variance by 3–15×. The
   7-byte short header + identity-keyed AEAD path is doing
   its job. This is the regime DRIFT was designed for: short,
   hop-bounded identity-routed messages.
2. **Throughput is wire-dependent, and the federation wire
   wins.** DRIFT-over-h2 / h2s clears 7 Gbps loopback on the
   same hardware where raw QUIC streams hit 1.9 Gbps. The
   prior framing ("DRIFT loses ~2× throughput to QUIC") was
   wrong — it conflated DRIFT-over-UDP (one slow wire choice)
   with the protocol's actual ceiling on its best wire.
3. **Iroh comparison validates the project category and
   reveals the lever.** Iroh over loopback hits 65 µs RTT p50
   on QUIC (its only wire); DRIFT hits 68 µs on UDP and 7 Gbps
   throughput on h2. The right comparison is per-axis, not a
   single number — and on most axes either DRIFT wins or
   DRIFT-with-the-right-wire wins.

The reason to pick DRIFT over Iroh is:
- **Wire choice** (Iroh is QUIC-only; DRIFT runs over UDP /
  TCP / WS / WebTransport / Tor / DoH-over-Worker / h2s, with
  measurably different throughput characteristics per wire so
  you can pick what your environment supports).
- Federation (Iroh has relay-fallback, not Matrix-style
  bridge-to-bridge with discovery primitives).
- Browser-native WASM (Iroh's WASM is roadmapped; DRIFT ships
  it today, byte-for-byte wire-compatible).

The reason to pick Iroh over DRIFT is the n0 organizational
backing, the shipping 1.0-rc.1 milestone, and a narrower
protocol surface (one wire to maintain instead of seven+).

## Reproducing

The four-protocol bench harness is `drift-bench/`. Add iroh as
a workspace member dep; `cargo run -p drift-bench -- --protocol
iroh --mode server --workload handshake`. The companion
`drift-bench/docker/` rig runs the same suite in a two-container
shared-network setup with optional `tc/netem` shaping; the
loopback numbers above are the single-host baseline.
