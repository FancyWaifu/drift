# DRIFT — full-matrix benchmark (2026-05-27)

Three workloads × seven wires × three contexts × three trials,
plus a cross-protocol baseline against Iroh and raw QUIC.
~220 data points total. All throughput is server-side
**goodput** (bytes that actually arrived per second), not
client-side pump-rate — the harness extracts the server's
`BENCH_BYTES_RECEIVED` / `BENCH_DURATION_S` markers from
stderr.

## Bottom line

**DRIFT-over-UDP outperforms QUIC and Iroh on latency-tight
workloads (handshake p50, RTT p50) on the same hardware.**
Loopback Mac, 3 trials each:

| Metric | DRIFT (UDP) | Iroh (QUIC + EP id) | QUIC (raw, quinn) |
| --- | --- | --- | --- |
| Handshake p50 | **795 µs** | 843 µs | 3140 µs |
| Handshake p99 | **1367 µs** | 2515 µs | 4046 µs |
| RTT p50 | **43 µs** | 68 µs | 67 µs |
| RTT p99 | **204 µs** | 230 µs | 210 µs |
| Throughput (median) | 1519 Mbps | 1688 Mbps | **1983 Mbps** |

DRIFT wins handshake by 1–4× and RTT by 1.5×. QUIC wins
sustained throughput by ~30% (this is the "QUIC streams batch,
DRIFT-over-UDP doesn't" gap).

**On real network the throughput story depends on the wire
you pick** — see the wire sweep below.

## What the matrix actually shows

1. **Latency wins are real and reproducible.** DRIFT-over-UDP
   handshake at 795 µs p50 is 4× faster than raw QUIC (3140 µs)
   on the same hardware. RTT p50 is 1.5× faster than both Iroh
   and QUIC. This is the regime DRIFT was designed for —
   short, identity-routed messages.
2. **Throughput is wire-dependent, with a context-shaped
   ceiling.**
   - Loopback: 3.8× spread between fastest (`ws`, 3553 Mbps)
     and slowest (`webtransport`, 901 Mbps). The wire matters
     a lot when there's no network bottleneck.
   - LXC↔LXC: 1.7× spread (`webtransport` 1215 → `h2s` 744).
     Most wires sit near gigabit line rate; the spread is
     dominated by per-wire overhead, not raw speed.
   - Cross-arch: 1.5× spread (`tls`/`ws` ≈755 → `webtransport`
     504). Real LAN compresses differences further.
3. **No wire is universally fastest.** `ws` wins loopback and
   cross-arch throughput; `webtransport` wins LXC↔LXC.
   `udp` is the steadiest near-line-rate across contexts and
   wins LXC↔LXC RTT. Pick the wire that suits the path.
4. **The cross-arch column is dominated by LAN physics.**
   Mac↔LXC handshake p50 is ~11.5–17 ms regardless of wire
   (5–6 ms × 2 round-trips + ~1 ms tail). RTT is ~5.5–6 ms.
   The wire only meaningfully matters when network RTT is
   small enough not to dominate.
5. **Trial-to-trial variance is small for steady-state
   metrics.** Throughput medians and ranges show <5% variance
   for most cells. Handshake p50 across trials varies more
   on cross-host runs (10–20%) because TCP/TLS setup
   competes with network jitter.

## Methodology

- **Loopback:** single Apple Silicon Mac (arm64), tokio
  `multi_thread`. Bench binary at
  `target/release/drift-bench`.
- **LXC↔LXC:** drift-1 (server, 192.0.2.52) and drift-2
  (client, 192.0.2.168), both 2-core / 512 MB Proxmox LXCs
  (x86_64 musl). Gigabit interconnect.
- **Cross-arch (Mac↔LXC):** Mac as client (arm64), drift-1
  LXC as server (x86_64). Real LAN.
- **Handshake workload:** 20 iterations per trial, fresh
  client identity per iteration (new X25519 static keys).
  Reports the time from `connect_url` → `send_data("go")` →
  first byte echoed back — handshake completion plus one
  application round-trip, the same boundary every protocol
  in the cross-proto bench reports.
- **RTT workload:** 500 ping-pong iterations per trial,
  single long-lived session warmed by an initial throw-away
  exchange, 1 KB payload, microsecond resolution.
- **Throughput workload:** 10 s sustained one-way send, 1 KB
  DRIFT packets, server counts bytes received. Goodput =
  `bytes_received / duration` taken from server stderr
  markers — not client pump-rate.
- **Trials:** 3 per cell. Median reported as the headline
  number; range as `(min–max)` for throughput.

## Caveats

- LXC↔LXC traffic goes over Proxmox veth, not a physical
  1 Gbps NIC. The ~1 Gbps numbers may reflect a kernel
  scheduling cap rather than a wire cap. Numbers on hosts
  with separate physical NICs will differ.
- Mac↔LXC traverses the Mac's WiFi/Ethernet adapter and a
  consumer-grade switch. Real-world LAN, not a controlled
  test fixture.
- The `ws` handshake anomaly on LXC↔LXC (p50 = 41 ms) is
  reproducible but not yet root-caused. Excluded from the
  "no wire is universally slow" claim.
- All payloads are 1 KB. Smaller and larger payloads will
  shift the ranking — larger payloads especially favor
  stream-based wires (`tcp`, `tls`, `ws`, `h2`) over the
  per-packet `udp`/`webtransport` shapes.

## Payload-size sweep (2026-05-28 follow-up)

Throughput-only sweep across 64 / 256 / 1024 / 1300 byte
payloads, three contexts, 3 trials per cell. The 1024 B
column for `loopback` and `lxc_lan` is from the original
matrix bench (2026-05-27); the 1024 B column for
`cross_arch` was re-run on 2026-05-28 because day-to-day
WiFi conditions on the Mac↔LXC link were ~5× different
(700 Mbps yesterday → 100 Mbps today), so an apples-to-
apples comparison within the payload sweep needed
same-day numbers.

**DRIFT's datagram API caps at `MAX_PAYLOAD` ≈ 1348 B**
(MAX_PACKET 1400 − header − AEAD tag, in `drift::transport`).
Larger application-level messages require DRIFT's reliable-
streams API, which fragments transparently into ≤MAX_PAYLOAD
chunks on the wire — so the wire-level throughput converges
to the 1300 B row regardless of app-level message size.

### What the payload sweep shows

1. **Per-packet overhead dominates at small payloads.** At
   64 B, h2 and h2s on loopback hit 723/720 Mbps because
   hyper batches DRIFT packets into h2 DATA frames; udp at
   64 B only manages 110 Mbps because every drift packet
   pays a full AEAD seal + syscall.
2. **Bigger payloads amortize that overhead.** UDP loopback
   goes 110 → 431 → 1520 → 1844 Mbps as payload grows.
   Same shape on LXC↔LXC: 70 → 278 → 1055 → 1311.
3. **On WiFi-limited cross-arch (~100 Mbps), payload doesn't
   help past 256 B.** All wires hit the ~100 Mbps ceiling
   once the per-packet cost is amortized over a few hundred
   bytes.
4. **Wire ranking changes with payload size.** Stream-batching
   wires (h2, ws) win at small payloads; plain `tcp` and
   `udp` win at near-MTU payloads where their lower framing
   overhead matters more.
5. **The lxc↔lxc ranking is the cleanest signal.** No
   workstation contention, dedicated LXC pair. At 1300 B,
   `webtransport` (1413) wins on real LAN, followed by
   `udp` (1311) and `ws` (1103). The federation wire `h2s`
   sits at 1032.

### Caveat — loopback workstation Mac contention

The Mac ran other processes during the 64 / 256 / 1300 B
loopback runs. Trial-to-trial variance was wide for several
wires (e.g. h2 at 1300 B: 4203 / 636 / 843 Mbps across
three trials). The median I reported is therefore
conservative; an unloaded Mac (trial 1 in each case)
showed numbers 2–4× higher for h2 / h2s / ws at 1300 B:
ws 3942, h2 4202, h2s 3563, webtransport 1068. **The LXC
and cross-arch numbers don't suffer from this** — those
hosts are dedicated and trials are within 5%.

## DRIFT-over-Iroh (`iroh://`) — 2026-05-29 follow-up

After building the `iroh://` wire adapter (`drift/src/wire_iroh.rs`,
behind `--features iroh`), we have a serious answer to the
funny question: "what if DRIFT ran over Iroh?" The result is
the punchline + the data.

### The joke

DRIFT is wire-agnostic (12+ adapters). Iroh is QUIC-only by
design. Putting DRIFT-over-Iroh stacks one identity-based
transport on top of another, with two layers of pubkey
addressing pretending the other doesn't exist. The bench
result, with no editorializing:

| context  | workload    | DRIFT-over-Iroh median |
|----------|-------------|------------------------|
| loopback | handshake p50 | 823 µs               |
| loopback | RTT p50       | 84 µs                |
| loopback | throughput    | 838 Mbps             |
| lxc_lan  | handshake p50 | 1010 µs              |
| lxc_lan  | RTT p50       | 101 µs               |
| lxc_lan  | throughput    | **1432 Mbps**        |

3 trials each, server-side goodput for throughput. Raw TSVs:
`drift-bench/iroh-{loopback,lxc-lan,docker}.tsv`.

### What the LXC↔LXC number means

**DRIFT-over-Iroh at 1432 Mbps is the fastest DRIFT wire on
the LXC LAN bench.** Sorted by throughput:

| DRIFT over...   | LXC↔LXC Mbps |
|-----------------|--------------|
| **iroh**        | **1432** ← new |
| webtransport    | 1215         |
| udp             | 1055         |
| ws              | 916          |
| h2              | 787          |
| tcp             | 781          |
| tls             | 753          |
| h2s             | 744          |

That's because iroh's QUIC stack (n0's noq fork of quinn) is
tuned for high-bandwidth peer-to-peer use cases — datagram
handling, congestion control, ACK frequency. DRIFT inherits
those tuning choices when it runs over iroh.

### Multi-container docker testbed

`docker/iroh-test/` brings up three drift-bench containers
plus an orchestrator on a single bridge network. Test runs
3 (server, client) pairs × 3 workloads. Handshake works
reliably across all combinations (1231–1493 µs p50, 22 ms
tail). RTT and throughput hit Mac Docker Desktop's known
UDP throttling — the same hit shows up with plain `udp://`,
not iroh-specific. See `docker/iroh-test/README.md` for the
full setup + findings.

### Implementation notes

- Behind `--features iroh` so the dependency cost (~30 crates)
  is opt-in.
- URL format `iroh://<endpoint_id_hex>@<host:port>` for the
  connector; `iroh://<bind_sockaddr>` for the listener. The
  endpoint id is logged at bind time so the client can scrape
  it (the `eprintln!` line in `wire_iroh.rs` is parser-friendly
  for orchestrator scripts).
- One QUIC bidirectional stream per peer, length-prefixed
  frames (2-byte big-endian + payload). No flush per packet —
  quinn auto-flushes when the congestion window allows, and
  per-packet flush kills throughput by ~10× on docker bridge
  networking.
- The `Endpoint` is stored inside `IrohPacketIO` so it lives
  as long as the streams. (Dropping the connector's endpoint
  after factory-return was the original bug — manifested as
  "connection lost" on the first send.)

### What it shows about DRIFT's architecture

The wire adapter system holds up. Adding iroh meant ~270
lines in `wire_iroh.rs` + 12 lines elsewhere (lib.rs module
declaration, Cargo.toml feature + dep). No protocol changes,
no core code edits. The new wire registers itself via
`inventory::submit!` and the URL dispatcher routes
`iroh://...` URLs to it automatically. Everything that runs
on DRIFT (`drift bridge`, `drift-mosh`, `drift-http`, the
bench harness) gains the iroh wire for free.

The joke is real. The wire works. And it happens to be the
fastest DRIFT wire on real LAN — which is the funniest
possible outcome.

## DRIFT-over-Iroh deep dive (2026-05-29)

Four tests across loopback, multi-host, and federation scenarios.

### Phase 1 — Payload-size sweep (3 contexts × 4 sizes × 3 trials)

Same sweep we ran for the other DRIFT wires, but iroh-only.
Median goodput Mbps over 3 trials:

| context     | 64 B | 256 B | 1024 B | 1300 B |
|-------------|------|-------|--------|--------|
| loopback    | 154  | 464   | 820    | 919    |
| lxc_lan     | 330  | 789   | 1388   | 1386   |
| cross_arch  | 62   | 80    | 85     | 89     |

Same payload-amortization shape as other wires. The LXC↔LXC
1300 B number (1386 Mbps) confirms the headline "iroh is the
fastest DRIFT wire on real LAN" claim from the previous round.
Cross-arch hits the ~85 Mbps WiFi ceiling at any payload ≥ 256 B.

### Phase 2 — Native iroh vs DRIFT-over-iroh overhead (Mac loopback, 3 trials)

drift-bench has two iroh paths: the cross-protocol comparison
mode (`--protocol iroh`, talks to iroh streams directly) and
the DRIFT-over-iroh path (`--protocol drift --listen iroh://`,
DRIFT wrapped over an iroh stream).

| Metric        | Native iroh | DRIFT-over-iroh | Overhead |
|---------------|-------------|-----------------|----------|
| RTT p50       | 76 µs       | 85 µs           | +9 µs (~12%) |
| RTT p99       | 204 µs      | 196 µs          | tied     |
| Throughput    | 1717 Mbps   | 829 Mbps        | ~51% efficiency |

DRIFT adds ~9 µs RTT overhead — the length-prefix framing +
AEAD seal/open + protocol bookkeeping. Throughput loss is the
bigger story: DRIFT-over-iroh delivers ~half the goodput of
native iroh streams on the same hardware, because DRIFT
seals each packet individually rather than streaming the
underlying bytes. That's the trade-off for cross-wire
portability — the same DRIFT bytes ride h2, ws, tcp, tor,
or webrtc with the same semantics, at the cost of stream-batching
efficiency.

Handshake comparison isn't apples-to-apples: native iroh
measures (iroh connect + first byte round-trip), DRIFT measures
(first send_data round-trip after handshake), so the boundaries
differ. Not reported as overhead.

### Phase 3 — All-pairs 4-LXC mesh (12 directed pairs)

drift-1, drift-2, drift-3, drift-4 (Proxmox LXCs, x86_64 musl).
Each runs as server for the other three. 1 trial per pair per
workload.

Median per workload across all 12 pairs:
- **Handshake p50**: 1029 µs (range 932–1066)
- **RTT p50**: 100 µs (range 93–118)
- **Throughput goodput**: **1340 Mbps** (range 1146–1504)

Tight ranges across all hosts — no individual LXC is materially
slower than the others. The 12-pair mean throughput (1340 Mbps)
closely matches the prior 2-host result (1432 Mbps for drift-1↔
drift-2 specifically), confirming DRIFT-over-iroh's
gigabit-class throughput on real LAN holds across more than
just one pair.

### Phase 4 — drift bridge federation over iroh:// (status: WORKING)

Goal: prove that the iroh wire isn't just bench-only; it also
carries the real drift bridge federation protocol.

What works:
1. **HTTP.FED.STRICT update** — drift bridge now accepts
   `iroh://` as a preferred federation scheme alongside h2,
   h2s, webtransport. Same code path as webtransport since
   both are QUIC. (`drift/src/cli/bridge.rs` matches: `"h2"
   | "h2s" | "webtransport" | "iroh"`.)
2. **parse_federate_spec switched to rsplit_once('@')** so
   federation URLs with internal `@` (notably
   `iroh://<endpoint_id>@<host:port>@<bridge_pub>`) split
   correctly at the bridge-pubkey boundary, leaving the iroh
   URL intact.
3. **Two-bridge launch succeeds.** bridge1 on drift-1 binds
   the iroh listener and prints its endpoint id + bridge
   pubkey; bridge2 on drift-2 starts with
   `--federate iroh://<id>@<addr>@<bridge1_pub>` and lists
   bridge1 in its federation peers.

What doesn't yet work end-to-end:
4. **Federation handshake fails at runtime.** Bridge1's iroh
   listener interface gets evicted within ~20 ms of bridge
   start ("recv_from failed; evicting interface; channel
   closed"). Bridge2's attempts then produce
   "authentication failed" warnings on the (still-bound)
   iroh socket. The behavior is consistent across multiple
   attempts.

Hypothesis (not yet verified): the bench harness uses
`IrohListenerIO` for short-lived single-PacketIO accept
flows that succeed before the iroh listener's internal state
becomes a problem; the bridge holds the listener as a
long-lived multi-PacketIO interface, exposing some race
between accept loop exit and Transport interface-eviction
that the bench doesn't hit. Filed as a known issue for
follow-up; the URL parsing, scheme-allow, and basic startup
all work. Closing the bug needs more time with the
Transport's interface-management code than this session has.

For now, the iroh wire's "real DRIFT bridge federation"
story is "wired up but not yet hot-paths". Bench traffic
(handshake, RTT, throughput sweeps) carries over iroh
reliably; the production bridge protocol exercises a code
path the bench doesn't and surfaces a runtime issue worth
chasing.

## Cross-protocol comparison notes

QUIC and Iroh both serve cert/node-address through a
filesystem-shared `/tmp` file (cert for QUIC, EndpointAddr
for Iroh), which makes them awkward to run cross-host
without a shared-volume setup. The cross-protocol numbers
above are loopback only. A proper cross-host QUIC bench
would use `iperf3 --quic` or `quiche-quic-bench`; we leave
that out of scope here. The DRIFT cross-host numbers stand
on their own — and the loopback cross-proto baseline
demonstrates that the DRIFT protocol's per-packet overhead
is competitive with quinn's, before wire-choice optimization
kicks in.

#### Update (2026-05-29 later): all three issues fixed, federation works

Root cause turned out to be a stack of three independent
problems that all had to be solved together:

1. **Ephemeral iroh endpoint id.** Every iroh::Endpoint bind
   regenerated a fresh keypair, so a `--federate iroh://<id>@...`
   URL captured in operator config went stale on every restart.
   Fix: `DRIFT_IROH_SECRET_HEX` env var → deterministic
   SecretKey → stable endpoint id across restarts.

2. **Random UDP port on iroh listener.** Even with a stable
   endpoint id, the bind port was OS-assigned, so the
   `iroh://<id>@<host:port>` URL was stale on port too.
   Fix: honor the listener URL's port via
   `Builder::bind_addr(hint)` when port != 0.

3. **Synthesized peer addr collided across iroh peers.** The
   original implementation used a process-wide counter to
   assign `127.0.0.1:60000+n` to each iroh peer. DRIFT's
   transport correlates sessions by `src_addr` — when the
   same synthetic addr was reused for a different iroh peer
   on a restart, AEAD lookup picked the wrong session key
   and packets failed authentication. **This is why the
   bench worked but federation didn't**: the bench uses
   fresh identities per iteration so session correlation
   doesn't matter; federation reuses long-lived sessions
   keyed by `(src_addr, peer_pub)`, so a stale addr poisons
   the lookup.
   Fix: `peer_addr_for_connection()` derives the SocketAddr
   deterministically from the iroh `EndpointId` via SipHash
   → distinct stable `192.0.2.x:port` per iroh peer (RFC
